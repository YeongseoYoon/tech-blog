# Blog Write — 기술블로그 집필 스킬

리서치 자료를 기반으로 이 블로그의 스타일에 맞는 기술 포스트를 작성한다.

## 이 블로그의 문체

기존 포스트들에서 추출한 스타일 가이드. 상세 예시는 `references/style-guide.md` 참조.

### 톤
- **자연스러운 한국어 경어체** — "~습니다", "~입니다" 기반
- **개인 경험 기반 도입** — "얼마 전 ~를 진행하면서", "~를 다루면서 어려움을 겪었던 적이"
- **독자와 함께 탐구하는 느낌** — "조금 더 깊게 들어가볼까요?", "살펴보겠습니다"
- **적절한 유머** — summary에 말장난이나 위트 (예: "한 걸음 closure 내 맘", "Date객체는 나가있어")

### 구조 패턴
1. **도입부** (2~3문단): 개인 경험 또는 배경 설명으로 시작 → 글의 목적 안내
2. **배경/문제점** (H1): 기존 방식의 한계, 이 기술이 필요한 이유
3. **핵심 내용** (H1 + H2): 개념 설명 → 코드 예제 → 상세 해설
4. **실무 활용** (H1): 실제 사용 패턴, 주의사항
5. **마무리** (선택적): 간결한 정리 또는 다음 글 예고

### 코드 예제 원칙
- 단순 → 복잡 순서로 점진적 제시
- 코드 블록 직후에 "위 코드에서 일어나는 일을 단계적으로 살펴보겠습니다" 식의 단계별 해설
- 실행 결과를 주석으로 포함 (예: `// 1`, `// "hello"`)
- 비교 예제 활용 — 나쁜 예 vs 좋은 예, 이전 방식 vs 새 방식

## Frontmatter 규칙

```yaml
---
title: "제목" # 한국어, 기술 용어는 영문 유지
date: "YYYY-MM-DDTHH:mm:ss.sssZ" # ISO 8601, 작성일 기준
summary: "위트 있는 한 줄 요약" # 제목과 관련된 말장난이나 유머
tags: ["태그1", "태그2"] # 기존 태그 재사용 우선, 대문자 (JavaScript, TypeScript, DEV 등)
---
```

## 파일명 규칙
- 케밥 케이스: `topic-name.md`
- 영문: 주제를 영문 키워드로 요약
- 예: `closure.md`, `tree-shaking.md`, `browser-cookie.md`

## 마크다운 규칙
- H1(`#`)은 주요 섹션 구분에 사용
- H2(`##`)는 하위 섹션
- H3(`###`)은 세부 항목 (번호 매기기와 함께: `### 1. 제목`)
- 코드 블록에 언어 태그 필수: ```js, ```tsx, ```css 등
- 이미지: `<figure><img src="/static/images/..." alt="..." /><figcaption>...</figcaption></figure>`
- 외부 링크는 인라인: `[텍스트](URL)`

## AI 티 제거

초안과 리뷰 반영본을 완성한 뒤, 최종 저장 전에 전역 `humanize-korean` 스킬을 사용해 AI 특유의 번역투와 문체를 보수적으로 점검한다.

- 장르는 `블로그`, 강도는 `보수`, 최소 심각도는 `S1`을 기본값으로 둔다.
- 의미·주장·수치·날짜·고유명사·직접 인용·기술 용어는 바꾸지 않는다.
- frontmatter, 제목 계층, URL, Markdown 링크, 이미지 경로, HTML, 코드 블록, 인라인 코드는 보호한다.
- `humanize-korean` 결과를 그대로 덮어쓰지 않는다. 원본과 diff를 확인하고 근거가 있는 국소 수정만 최종본에 반영한다.
- 변경률이 30%를 넘거나 필자의 개성·원저자의 어조가 약해지면 결과를 폐기하고 원문을 유지한다.
- 외부 아티클 번역에서는 아래 번역 규칙과 원문 충실도가 `humanize-korean`보다 우선한다.

## 외부 아티클 번역 게시

### 저작권과 출처

- 원저자의 전문 번역 허락을 먼저 확인한다. 허락 없이 전문 번역을 게시하지 않는다.
- 본문 상단에 번역 사실, 원저자 크레딧, 원문 링크백을 명시한다.
- 글 하단에 원저자 소개를 둔다.

### Korean FE Article 관례

Korean FE Article의 기존 번역글을 대조 기준으로 삼아 다음 원칙을 지킨다.

- 번역을 시작하기 전에 로컬 Korean FE Article 저장소의 `.hanspell-typos`와 `references/korean-fe-terminology.md`를 순서대로 읽는다. 두 파일이 충돌하면 KFA 공식 `.hanspell-typos`를 우선하고 작업용 용어집을 함께 수정한다.
- 초벌 번역과 윤문 전에 `references/translation-naturalness.md`를 읽고 의미 골격 → 자연스러운 한국어 → 원문 역대조의 3단계를 적용한다.
- 원문 URL을 `scripts/check-kfa-duplicate.mjs`로 검사한다. KFA의 전체 open/closed 이슈·PR 또는 모든 연도 번역 파일에서 동일 URL이 나오면 번역을 중단하고 중복 링크를 보고한다.

- 자연스럽고 간결한 `~습니다/~입니다`체를 사용한다.
- 내용을 요약·각색·추가하지 않고 원문의 주장, 문단 흐름, 강조 의도를 보존한다.
- 직역투보다 한국어 문장 호흡을 우선하되 의미와 논리 관계는 바꾸지 않는다.
- 은유의 단어를 기계적으로 옮기지 말고 문맥에서 수행하는 기능을 번역한다. 다만 글 전체를 관통하거나 반복되는 핵심 은유는 삭제하지 않고 한국어에서 이해되는 형태로 보존한다.
- 추상명사가 연달아 나오면 원문의 행위자·행동·대상을 찾아 동사 중심 문장으로 풀어 쓴다.
- 대명사와 생략된 주어의 대상이 원문에서 분명하면 한국어 명사구로 밝혀 쓴다. 원문 자체가 의도적으로 모호하면 임의로 대상을 만들어내지 않는다.
- 기술 용어와 고유명사는 용어집과 업계에서 통용되는 표기를 사용하고 한 글 안에서 일관되게 쓴다.
- 원문의 볼드·이탤릭·목록·인용·코드·인라인 코드를 가능한 한 같은 위치에 유지한다.
- 원문 이해에 꼭 필요한 설명만 `[역자 주: ...]`로 덧붙인다. 원문에 없는 의견이나 해설을 본문처럼 삽입하지 않는다.
- 최종 검토 때 최근 Korean FE Article 번역글 2~3편과 제목, 문체, 용어, 문단 호흡을 대조한다. 공개 선례에서 확인되지 않은 형식을 공식 규칙처럼 단정하지 않는다.

### 원문과 링크 수집

- 브라우저 자동화 도구로 원문 전체를 수집한다. 가능하면 저자의 원본 Markdown을 우선한다.
- 원문의 `href + 링크 텍스트`, 이미지 URL, 코드, 강조 요소의 목록을 별도로 추출해 누락을 검사한다.
- 링크 URL은 바꾸지 않고 앵커 텍스트만 번역한다.
- `_workspace/translations/{slug}/manifest.json`에 원문 URL·제목·저자·게시일·확인일·허락 확인·KFA 중복 검사 결과와 이슈 URL·본문 링크 목록·이미지 목록·구조 집계를 기록한다.
- 원문 전체 복제본이나 비공개 허락 메시지는 기본적으로 커밋하지 않는다. 허락 증빙은 공개 가능한 참조 위치와 확인 사실만 기록한다.

### 개인 블로그와 KFA 제출본 분리

- `posts/{slug}.md`는 tech-blog 전용 최종본이다. `[번역]` 제목, frontmatter, 로컬 이미지, 저자 소개 규칙을 유지한다.
- KFA 제출본은 로컬 `korean-fe-article` 저장소에 `{년도}/{월}/{번역자명} - {원문 제목}.md`로 별도 생성한다.
- KFA 제출본은 첫 줄 `# 번역 제목`, 다음 블록 `> 원문: {URL}` 형식을 사용하며 tech-blog frontmatter, `[번역]`, `translate` 태그를 복사하지 않는다.
- 이미지 정책은 저장소별로 다르게 적용한다. tech-blog는 로컬 호스팅하고 KFA 제출본은 원문 이미지 URL을 보존한다.
- KFA 제출본을 만든 뒤 그 저장소의 `translate-full`, 5관점 리뷰, glossary, final-check, PR 템플릿을 따른다.

### 이미지와 임베드

- 이미지는 외부 URL 대신 `public/static/images/`에 내려받아 로컬 호스팅한다.
- 파일명은 `{slug}-01.ext`처럼 글 슬러그 접두사를 붙인다.
- 본문에서는 `<figure><img src="/static/images/..." alt="..." /><figcaption>...</figcaption></figure>` 형식을 사용한다.
- 재현하기 어려운 임베드는 원문 링크로 안내하거나 허락 범위 안에서 스크린샷·GIF로 대체한다.

### Frontmatter와 검증

- 파일명은 원문 슬러그를 영문 케밥 케이스로 사용한다.
- `date`는 번역 게시일 기준 ISO 8601을 사용한다.
- `title`은 `[번역] {한국어 번역 제목}` 형식으로 작성한다. `[번역]` 뒤에 공백 한 칸을 둔다.
- `tags`는 기존 태그를 우선하고 `translate`를 함께 추가한다.
- dev 서버에서 `/blog/{slug}`를 열어 제목, 날짜, 태그, 본문, 강조, 코드, 링크, 이미지를 확인한다.
- 원문 링크 목록과 최종 Markdown 링크 목록을 대조해 URL 변경·누락이 없는지 검증한다.
- `npm run check:translation -- posts/{slug}.md _workspace/translations/{slug}/manifest.json`을 실행하고 실패 항목을 모두 고친다.
- 원문이 나중에 변경됐는지 확인할 수 있도록 `sourceCheckedAt`과 가능한 경우 원문 해시를 manifest에 남긴다.
