# Blog Review — 기술블로그 리뷰 스킬

기술블로그 포스트의 품질을 다각도로 검토하고 구체적 개선안을 제시한다.

## 검토 기준

검토 전에 frontmatter의 제목과 태그로 일반 글과 번역 글을 구분한다. `[번역]` 제목 또는 `translate` 태그가 있으면 아래 번역 전용 기준을 일반 글 기준보다 우선 적용한다. 번역문에는 개인 경험 도입부, 글의 재구성, 위트 있는 summary를 요구하지 않는다.

### 1. 기술적 정확성 (MUST FIX 대상)
- 코드 예제의 문법 오류, 로직 오류
- 기술 개념의 잘못된 설명
- 용어의 부정확한 사용
- 출처가 없는 주장

### 2. 가독성
- 도입부가 독자의 관심을 끄는가
- 글의 흐름이 논리적인가 (배경 → 개념 → 활용)
- 단락이 적절히 나뉘어 있는가 (한 단락에 한 아이디어)
- 코드 예제 직후에 충분한 해설이 있는가

### 3. 포맷 준수
- Frontmatter 필수 필드: title, date, summary, tags
- date가 ISO 8601 형식인가
- summary가 위트 있고 짧은가
- tags가 기존 태그와 일관되는가
- H1/H2/H3 계층이 올바른가
- 코드 블록에 언어 태그가 있는가

### 4. 독자 경험
- "왜"가 "어떻게" 전에 나오는가
- 코드 예제가 점진적으로 복잡해지는가
- 실무에서 바로 쓸 수 있는 정보가 있는가
- 글의 분량이 적절한가 (너무 짧거나 너무 길지 않은가)

### 5. 블로그 스타일 일관성
- 한국어 경어체 사용
- 개인 경험 기반 도입부
- 코드 예제 후 단계별 해설 패턴

### 6. 외부 아티클 번역 검증 (모두 MUST FIX)

- 전문 번역 허락 사실, 원저자 크레딧, 원문 링크백, 하단 원저자 소개가 있는가
- 원문의 제목·문단·제목 계층·목록·인용·코드·볼드·이탤릭·인라인 코드가 누락되거나 임의로 추가되지 않았는가
- 원문의 주장과 논리 관계를 요약·각색·확장하지 않았는가
- 숫자, 단위, 날짜, 고유명사, 직접 인용이 원문과 일치하는가
- 원문의 본문 링크 URL 집합과 번역문의 본문 링크 URL 집합이 정확히 일치하는가. 원문 링크백과 저자 소개 등 번역 게시용 링크는 별도로 구분했는가
- 이미지가 `public/static/images/`에 슬러그 접두사로 저장됐고 파일이 실제로 존재하는가. 출처와 사용 조건을 manifest에 기록했는가
- `blog-write/references/korean-fe-terminology.md`의 선호 표기를 일관되게 사용했는가
- `[역자 주: ...]` 외에 번역자가 추가한 의견이 본문에 섞이지 않았는가
- `humanize-korean` 적용 전후로 의미, 수치, 어조가 달라지지 않았는가
- `blog-write/references/translation-naturalness.md`를 읽고 은유 직역, 추상명사 중첩, 불명확한 대상, 영어식 명사화·결합 표현이 남았는가
- 자연스럽게 고치는 과정에서 원문의 반복 은유, 주장 강도, 인과 관계, 의도적인 모호함을 지우거나 새 설명을 보태지 않았는가
- 번역 manifest가 있고 원문 URL·확인일·허락 확인·구조 및 에셋 집계가 기록됐는가
- 자동 검사 명령이 성공했는가

## 검토 절차

1. 전체 글을 한 번 통독한다
2. Frontmatter를 먼저 검증한다
3. 섹션별로 기술 정확성을 확인한다
4. 코드 예제를 로직 수준에서 검토한다
5. 글의 흐름과 가독성을 평가한다
6. MUST FIX / NICE TO HAVE로 분류하여 피드백을 작성한다

번역 글은 원문, manifest, `blog-write/references/translation-naturalness.md`를 함께 읽고 항목별 대조표를 작성한다. 각 문단에서 `누가/무엇이 → 무엇을 한다 → 그 결과가 무엇인가`를 복원해 번역문과 대조한다. 원문을 읽을 수 없거나 하나라도 검증하지 못한 항목이 있으면 `검증 불가`를 MUST FIX로 분류하며 게시 승인 판정을 내리지 않는다.
