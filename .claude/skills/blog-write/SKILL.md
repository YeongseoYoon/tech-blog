# Blog Write — 기술블로그 집필 스킬

리서치 자료를 기반으로 이 블로그의 스타일에 맞는 기술 포스트를 작성한다.

## 이 블로그의 문체

기존 포스트들에서 추출한 스타일 가이드. 상세 예시는 `references/style-guide.md` 참조.

### 톤
- **자연스러운 한국어 경어체** — "~습니다", "~입니다" 기반
- **개인 경험 기반 도입** — "얼마 전 ~를 진행하면서", "~를 다루면서 어려움을 겪었던 적이"
- **독자와 함께 탐구하는 느낌** — "조금 더 깊게 들어가볼까요?", "살펴보겠습니다"
- **적절한 유머** — summary에 말장난이나 위트 (예: "한 걸음 closure 내 맘", "Date객체는 나가있어")

### 구조 패턴
1. **도입부** (2~3문단): 개인 경험 또는 배경 설명으로 시작 → 글의 목적 안내
2. **배경/문제점** (H1): 기존 방식의 한계, 이 기술이 필요한 이유
3. **핵심 내용** (H1 + H2): 개념 설명 → 코드 예제 → 상세 해설
4. **실무 활용** (H1): 실제 사용 패턴, 주의사항
5. **마무리** (선택적): 간결한 정리 또는 다음 글 예고

### 코드 예제 원칙
- 단순 → 복잡 순서로 점진적 제시
- 코드 블록 직후에 "위 코드에서 일어나는 일을 단계적으로 살펴보겠습니다" 식의 단계별 해설
- 실행 결과를 주석으로 포함 (예: `// 1`, `// "hello"`)
- 비교 예제 활용 — 나쁜 예 vs 좋은 예, 이전 방식 vs 새 방식

## Frontmatter 규칙

```yaml
---
title: "제목" # 한국어, 기술 용어는 영문 유지
date: "YYYY-MM-DDTHH:mm:ss.sssZ" # ISO 8601, 작성일 기준
summary: "위트 있는 한 줄 요약" # 제목과 관련된 말장난이나 유머
tags: ["태그1", "태그2"] # 기존 태그 재사용 우선, 대문자 (JavaScript, TypeScript, DEV 등)
---
```

## 파일명 규칙
- 케밥 케이스: `topic-name.md`
- 영문: 주제를 영문 키워드로 요약
- 예: `closure.md`, `tree-shaking.md`, `browser-cookie.md`

## 마크다운 규칙
- H1(`#`)은 주요 섹션 구분에 사용
- H2(`##`)는 하위 섹션
- H3(`###`)은 세부 항목 (번호 매기기와 함께: `### 1. 제목`)
- 코드 블록에 언어 태그 필수: ```js, ```tsx, ```css 등
- 이미지: `<figure><img src="/static/images/..." alt="..." /><figcaption>...</figcaption></figure>`
- 외부 링크는 인라인: `[텍스트](URL)`

## 외부 아티클 번역 게시

영어 등 외부 아티클을 번역해 이 블로그에 올릴 때의 방식. (예: Addy Osmani, "Earning taste and judgment" → `posts/earning-taste-and-judgment.md`)

### Korean FE Article 관례
- 번역을 시작하기 전에 `references/korean-fe-terminology.md`를 반드시 읽고 기술 용어의 기본 표기를 적용한다.
- 최근 Korean FE Article 번역글 2~3편을 대조해 제목, 문체, 용어, 문단 호흡을 확인한다.
- 자연스럽고 간결한 **~습니다/~입니다체**를 사용한다.
- 내용을 요약·각색·추가하지 않고 원문의 주장, 문단 흐름, 강조 의도를 보존한다.
- 직역투보다 한국어 문장 호흡을 우선하되 의미와 논리 관계는 바꾸지 않는다.
- 기술 용어와 고유명사는 용어집과 업계에서 통용되는 표기를 사용하고 한 글 안에서 일관되게 쓴다.
- 원문의 볼드·이탤릭·목록·인용·코드·인라인 코드를 가능한 한 같은 위치에 유지한다.
- 꼭 필요한 설명만 `[역자 주: ...]`로 덧붙인다. 공개 선례에서 확인되지 않은 형식을 공식 규칙처럼 단정하지 않는다.

### 전제 — 저작권
- **원저자의 번역 허락을 먼저 받는다.** 허락 없이 전문 번역을 게시하지 않는다.
- 허락 조건으로 거의 항상 **원저자 크레딧 + 원문 링크백**이 붙는다. 아래 두 가지로 충족한다.
  1. 본문 최상단(요약 아래)에 번역 명시 인용문:
     `> 이 글은 {저자}의 [{원제}]({원문 URL})를 원저자의 허락을 받아 번역한 글입니다.`
  2. 글 하단에 원저자 소개 한 문단(원문 author bio 번역).

### 원문 수집
- **Playwright MCP로 원문 페이지 전체를 가져온다** (요약 금지). 가능하면 저자의 원본 마크다운(예: GitHub raw)을 우선 사용한다.
- 방문 시 **하이퍼링크(href + 앵커 텍스트)와 이미지 URL 목록을 함께 추출**해 둔다. 누락 방지.

### 번역 원칙
- 문체는 이 블로그 톤과 동일한 **~습니다/~입니다체**. 원저자의 어투·강조(볼드/이탤릭)·문단 구조를 유지한다.
- **하이퍼링크는 URL을 절대 바꾸지 않고**, 링크 텍스트(앵커)만 번역한다. `[번역된 텍스트](원본 URL)` 형태로 원위치에 그대로 둔다.
- 코드·인라인 코드(`sleep()` 등)·수치는 원문 그대로.
- 자연스러운 한국어를 위해: 불필요한 콜론(:)은 평서문으로 전환, 이중 피동(`~되어집니다`) 금지, 영어 em dash 삽입구는 문장 분리 또는 관형절로.

### 링크·이미지가 깨지지 않게 (이 레포 규칙)
- **이미지는 외부 URL을 그대로 쓰지 말고 로컬로 내려받아 호스팅한다.** 원저자 사이트가 경로를 바꾸면 깨지기 때문.
  - 저장 위치: `public/static/images/`
  - 본문 참조: `<figure><img src="/static/images/{파일명}" alt="..." /><figcaption>...</figcaption></figure>`
  - 파일명은 글 슬러그 접두사를 붙여 충돌 방지 (예: `earning-judgment-01.png`)
- 영상 등 재현 불가한 임베드는 원문 링크로 안내하거나 스크린샷/GIF로 대체한다.
- 외부 하이퍼링크(참고 문헌 등)는 원본 URL 그대로 인라인 유지.

### Frontmatter / 파일명
- `date`는 **블로그 게시일(번역 완료일) 기준** ISO 8601.
- `title`은 `[번역] {한국어 번역 제목}` 형식으로 작성한다. `[번역]` 뒤에 공백 한 칸을 둔다.
- `summary`는 한 줄 요약으로 작성한다.
- `tags`는 주제에 맞는 기존 태그를 재사용하고 `translate`를 함께 추가한다.
- 파일명(슬러그)은 **원문 슬러그를 케밥 케이스로** 따른다 (예: `earning-taste-and-judgment.md`).

### 검증
- dev 서버(`npm run dev`)로 `/blog/{slug}` 렌더링 확인: 제목·날짜·태그·본문·링크·이미지가 모두 정상인지 본다.
- 원문과 최종 Markdown의 링크 목록을 대조해 URL 변경·누락이 없는지 확인한다.

## AI 티 제거

초안과 리뷰 반영본을 완성한 뒤 전역 `humanize-korean` 스킬로 보수적으로 점검한다.

- 기본 옵션: `장르: 블로그`, `강도: 보수`, `최소심각도: S1`.
- 의미·주장·수치·날짜·고유명사·직접 인용·기술 용어를 바꾸지 않는다.
- frontmatter, URL, Markdown 링크, 이미지 경로, HTML, 코드 블록, 인라인 코드를 보호한다.
- 결과를 그대로 덮어쓰지 말고 diff에서 근거가 있는 국소 수정만 반영한다.
- 변경률 30% 초과 또는 필자·원저자 어조 훼손 시 결과를 폐기한다.
- 외부 번역에서는 Korean FE Article 관례와 원문 충실도가 `humanize-korean`보다 우선한다.
